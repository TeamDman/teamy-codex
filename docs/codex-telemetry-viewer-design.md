# Codex telemetry viewer: investigation and implementation plan

Status: design only, 2 November 2026. No collector, viewer, configuration change or live capture has been implemented by this plan. Synthetic examples and tests should use invented commands and outputs. This work builds on the egui guide in the adjacent Teamy Docs checkout and its [proposed typed telemetry contract](https://github.com/TeamDman/teamy-docs/blob/b34b31de729973dca3aeb9d95627403599e7a69a/src/logging.md#preserve-field-types-before-crossing-ipc).

## Evidence and limits

- [Codex telemetry configuration](https://learn.chatgpt.com/docs/config-file/config-advanced#observability-and-telemetry) separates logs (`otel.exporter`), traces and metrics. Tool-call text requires logs; a trace-only receiver is insufficient. HTTP binary, HTTP JSON and gRPC are documented transports. Prompt logging is a separate opt-in. Do not enable any of them automatically.
- The installed executable reports `codex-cli 0.156.1`; the [upstream release](https://github.com/openai/codex/releases/tag/rust-v0.156.1) identifies tag `rust-v0.156.1`, commit `b412ff32c417f855c2b2d1581b77058eed87c84b`. This associates the reported version with source; the installed binary itself has not been reproducibly matched to that commit. At that tag, [`codex.tool_result`](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/otel/src/tool_result.rs) logs carry `tool_name`, `tool_namespace`, `call_id`, `duration_ms`, `success`, `output_truncated`, `arguments`, `output`, `agent_name` and MCP metadata. Its trace event intentionally includes lengths and metadata instead of arguments/output. The [default](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/protocol/src/config_types.rs) output preview limit is 2,048 UTF-8 bytes before a truncation notice; `output_truncated = false` only says this particular telemetry limit did not truncate it. Arguments and output can contain secrets. The result sequence is process-local, records completion order and resets on restart, not a universal start-order key. A [`codex.tool_decision`](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/otel/src/events/session_telemetry.rs) carries tool, call ID, decision and optional source.
- For a function tool the [logged payload](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/tools/src/tool_payload.rs) is its argument string, except [direct plaintext messages](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/tools/router.rs) are replaced with a placeholder. The release's [`exec_command` schema](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/tools/handlers/shell_spec.rs) has a `cmd` string and an optional `shell`, which can be omitted in favor of the default. A synthetic argument such as `{"cmd":"Get-Date","shell":"powershell"}` is therefore a plausible shape, not a captured event or proof that every PowerShell call names its shell. Other tools, wrappers and implicit shells can have different shapes. The result is the tool's log representation, which may already differ from complete raw process output. Local app agents and managed Work chats have different configuration boundaries; follow [developer settings](https://learn.chatgpt.com/docs/developer-settings) for the relevant product.
- CM's existing `EventCollector` layer and `Logs` widget demonstrate subscriber composition and an egui log pane. The inspected fork uses unbounded shared storage, clones all events on read, stores debug strings, ignores span context and depends on Serde. It is useful UI prior art, not yet a suitable typed or bounded OTLP store. Teamy Hyper Backup Explorer supplies another eframe/egui_tiles application pattern. See the Teamy Docs guide for revision-specific references.
- `teamy-tracing` revision `ed87c96878cfe3db00dc58b20004a2c860e2bd3d` is currently a composable Facet JSON formatter and record-locked writer. Callers own subscribers, filtering, sink lifecycle and files. It does not yet provide the proposed receiver, event model or egui UI. Its exact owned registry Facet graph differs from this checkout's Git-pinned Facet graph; reconcile type identities and dependency policy deliberately before exposing shared Facet types or upgrading a consumer. This plan does not authorize a release or migration.

## Collector unavailable: release-source analysis

The release [uses](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/otel/src/provider.rs) the SDK batch log exporter; its [lockfile](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/Cargo.lock) pins OpenTelemetry SDK and OTLP 0.31.0. The [SDK processor](https://github.com/open-telemetry/opentelemetry-rust/blob/v0.31.0/opentelemetry-sdk/src/logs/batch_log_processor.rs) sends into a bounded in-memory channel with nonblocking `try_send`. Defaults are 2,048 queued records, 512 per batch and a one-second schedule, subject to environment overrides; a full queue drops incoming records and emits a warning on the first drop. This is a record count, not a byte budget. Export runs on a background thread; cloning and enqueuing still happen on the emitting thread.

After an export attempt the processor clears that batch even on error, logs an SDK error and does not requeue it. The inspected [HTTP exporter](https://github.com/open-telemetry/opentelemetry-rust/blob/v0.31.0/opentelemetry-otlp/src/exporter/http/logs.rs) makes one client request per export call; lower transport retry behavior is not established here. Future batches can be attempted after the collector returns, but failed batches cannot be recovered by the processor and no durable spool is present in this inspected processor path. Do not infer the absence of any other separate Codex file from that observation. The HTTP exporter treats a successful HTTP status as success without inspecting the OTLP response body for partial success; the receiver must expose its own acceptance/drop diagnostics rather than rely on this sender noticing rejected records.

Provider initialization constructs the exporter and waits for a shutdown worker's startup handshake; source review does not prove an end-to-end startup latency or collector connection outcome across HTTP/gRPC. The provider offers a detached, timeout-bounded shutdown method, while its ordinary shutdown invokes the SDK synchronously; actual caller paths and total UI exit time need qualification. Logs can be lost during export failure, queue overflow, process exit or shutdown timeout. SDK warning visibility and `log_console` interaction are unverified. A minimal future qualification is a separately launched CLI with a temporary isolated Codex home, synthetic tool invocation and a controllable loopback OTLP endpoint: start with the endpoint absent, bring it up, stop it, and record delivered event IDs and startup/exit durations for HTTP and the selected configuration. This requires specific approval before changing settings or performing a live capture, and must not access real conversation data.

## Candidate API shape

Names are provisional. Keep the existing default formatter graph intact and place network and UI behind opt-in features or separate adapter crates if graph isolation requires it:

- A core `TelemetryRecord`/`TelemetryValue` and `RecordStore` API accepts owned typed records, returns bounded query pages or snapshots and exposes loss counters. An optional local `tracing` layer converts visited primitives and documented formatted fallbacks into the same records; the application installs it in its own subscriber.
- An optional `otlp-http` adapter exposes a caller-owned `Receiver::bind_loopback(config, sink)` and explicit shutdown handle. It decodes protocol objects into records and writes to the supplied sink without emitting those records back through tracing. A dedicated diagnostics handle exposes errors and counters.
- Optional `egui` widgets accept a store/query interface and UI state; they neither start a server nor create an eframe app. File and console consumers operate on the shared model with caller-supplied writers and independent failure/retention policies. The existing `FacetJson` layer and `SharedWriter` retain their present contracts.
- Teamy Codex owns a `CodexToolCall` adapter and eframe application, correlating source/session/call identifiers, preserving raw fields and showing partial results. No exact signature or feature name above is a stable API commitment.

## Proposed boundaries

1. **Typed records and storage:** add a reusable versioned Facet-backed event envelope, independent of network and UI. Preserve OTLP resource, scope and record attributes, their types, source/observed timestamps, trace/span IDs and unknown fields. Distinguish missing, invalid and explicitly truncated data. Preserve timing units, producer identity and sequence where supplied; never invent a complete ancestry or start time. Provide a bounded byte and record budget, explicit eviction/drop counters and a query interface that does not clone all history each frame. Reuse the Teamy Docs contract, with a documented mapping for values that cannot round-trip. Avoid first-party Serde APIs per TeamyStyle.
2. **Optional OTLP ingestion:** prototype a loopback-only listener owned and shut down by the caller. Start with OTLP/HTTP logs and the protocol actually qualified with Codex; add other transports or signals only when needed. Reject malformed/oversize requests, cap concurrent work, and acknowledge only according to a documented accepted/dropped policy, including OTLP partial-success behavior. The listener is not a substitute for a durable queue; define saturation and shutdown semantics and expose counters without logging ingested data. Binding failure must be visible. Default to loopback and do not open a firewall or advertise a network endpoint. Network dependencies must be optional; a separate adapter crate is an alternative if feature isolation or the dependency graph requires it.
3. **Sinks and local tracing:** adapt local `tracing` events and received OTLP records into the shared model while retaining their source identity. Keep subscriber and file ownership with the application. Offer explicit record consumers for console, a versioned file and the store; do not assume the existing `FacetJson` formatter accepts external records. Avoid routing received records back through `tracing` into an exporter: that can recurse, misattribute them or leak payloads. Diagnostics for receiver failures must not contain raw payloads or cause recursive emission. Explicitly specify persistence, disk errors, rotation/retention and replay before enabling file capture.
4. **Optional egui widgets:** reuse the existing log table's filtering and inspection ideas, not its unbounded storage. A widget reads paged/snapshotted data from an app-owned store; it does not own an eframe window, server or runtime. Support bounded presentation, selection and repaint notifications. Evaluate version alignment and whether a fork extension or a new widget is less costly after the data contract exists. The non-GUI library path must not require egui/eframe.
5. **Teamy Codex adapter and eframe shell:** normalize known event names into a tool-call view, retaining unknown attributes. Correlate decisions and results using source/session and call ID when present, allow missing/duplicate/out-of-order events and show uncertainty rather than fabricate starts. Display time, session/agent, tool, decision, duration, status and truncation; select a row to inspect the argument text and output. Recognize PowerShell only when the recorded tool and arguments support it; show the original text with readable multiline presentation, and never execute it. Keep generic widgets/store reusable and Codex parsing/presentation in this application. Long output needs virtualized or incremental display, copy controls and a visible truncation/loss indicator.

## Security and operational choices to settle

Telemetry may contain commands, output, paths, secrets and personal information even with prompts disabled. Default to no listener until explicitly started, loopback binding, bounded memory, no automatic persistence and no raw payloads in the receiver's own logs. Before storage, define configurable redaction and whether raw capture is opt-in; redaction cannot promise detection of all secrets. Define file permissions, retention, deletion and clear behavior across memory and disk; make persistence and export deliberate. Treat loopback as local transport, not authentication against other local processes. Do not infer an empty view means Codex produced no events.

## Milestones and acceptance

1. Write synthetic, version-labelled OTLP fixtures including decisions/results, PowerShell-shaped arguments, multiline Unicode, unknown attributes, truncated output, missing IDs and out-of-order/duplicate events. Document source mapping and dependency/Facet compatibility before changing public APIs.
2. Implement and test the typed model and bounded store: primitive and nested values, unknown-field round trips, source identity, limits, counters, concurrent access, shutdown and sink errors. No listener or GUI dependencies in the default formatter graph. Preserve the existing formatter/writer tests and no-recursive-logging contract.
3. Add a feature-gated loopback receiver. Synthetic HTTP client tests exercise content type, valid and malformed payloads, size and concurrency limits, partial acceptance, unavailable sink, saturation, bind failure and orderly shutdown. Verify non-loopback rejection and absence of retransmission loops. Keep receiver errors observable without recording payloads.
4. Add reusable egui components and a Teamy Codex shell with synthetic records. Test correlation, filtering, absent/unknown fields, duplicate and reordered events, output truncation, Unicode and very large histories. Manually check responsiveness, keyboard access, selection, clear and repaint; do not run a live sensitive capture as a routine test.
5. With specific approval for a controlled temporary configuration and synthetic-only live input, qualify the installed Codex version against the listener: actual fields, PowerShell fidelity, disabled/enabled console output, unavailable/restarted receiver, delivery/drop behavior and clean shutdown. Record version, results and cleanup. An offline capture or export failure must not be silently represented as complete. Changing the user's live Codex settings or capturing actual conversations requires separate specific confirmation.

Open choices include OTLP dependency and initial encoding, exact buffer and retention defaults, durable storage format, redaction policy, feature versus separate crate, dependency graph alignment, and the installed-version validation method. Resolve these with a small synthetic prototype and dependency review before committing to a public API.
